Secondary index for Iceberg tables

Apache XTable™ (Incubating) can keep a secondary index on a column of an Apache Iceberg table. The index maps each value of the column to the data files that hold it, and is stored as an Apache Hudi metadata table under .hoodie/ in the data path of the table. Using an index takes two parts:

  1. An XTable sync job builds the index and keeps it current.
  2. Spark sessions with the XTable Spark SQL extensions use the index for point lookups, in SQL queries and DataFrame reads alike. Queries do not change.

Building the index with a sync job​

Any XTable sync of the table builds the index when it has a Hudi target with the index settings: RunSync from the utilities jar, XTableSparkSync from the Spark runtime jar, or a Spark job that calls the XTable sync API. Add the Hudi target to the --datasetconfig of the job:

sourceFormat: ICEBERG
targetFormats:
  - HUDI
datasets:
  - tableBasePath: s3://bucket/warehouse/db.db/customer
    tableDataPath: s3://bucket/warehouse/db.db/customer/data
    tableName: customer
    namespace: db
    targetProperties:
      HUDI:
        xtable.hudi.target.table_version: '9'
        xtable.hudi.target.execution.engine: spark
        xtable.hudi.target.secondary.index.column: c_email_address

Run the sync with the jar that fits the deployment:

  • The utilities jar runs RunSync as a standalone Java process, for example a scheduled job or a service outside Spark. It builds the index in a local Spark session on one machine.
  • The Spark runtime jar runs XTableSparkSync on an existing Spark cluster, so the index build is distributed across the executors.
shell
# utilities jar, built from source, which starts a local Spark session for the
# index build. It bundles Spark 3.4, so add the Hudi Spark 3.4 bundle for the
# Spark engine.
java -cp xtable-utilities/target/xtable-utilities_2.12-<version>-bundled.jar:hudi-spark3.4-bundle_2.12-1.2.1.jar \
  org.apache.xtable.utilities.RunSync \
  --datasetConfig index_config.yaml

# Spark runtime jar, on a Spark cluster
$SPARK_HOME/bin/spark-submit \
  --class org.apache.xtable.spark.XTableSparkSync \
  --conf spark.serializer=org.apache.spark.serializer.KryoSerializer \
  xtable-spark-runtime_2.12-0.5.0-incubating.jar \
  --datasetconfig index_config.yaml

The Spark runtime jar needs the Hudi Spark bundle and the Iceberg libraries on the classpath, as described in Setting up Spark. Use it for large tables, because the index build reads every data file of the table and the utilities jar runs it on one machine.

The first sync builds the index from the current snapshot of the table, and each later sync adds the changes of the new snapshots.

  • An index covers one top level column of type string, int or bigint, and its column does not change. A sync with another column fails before it commits.
  • Other xtable.hudi.target.* settings tune the index, for example the xtable.hudi.target.metadata.record.index.* file group counts.
  • To remove the index, remove the Hudi target from the sync job and delete .hoodie/ under the data path of the table. The data files of the table are not changed. A later sync with another column builds a new index.

Querying with the index​

Setting up Spark​

The extensions need Spark 3.x with Scala 2.12, the Iceberg Spark runtime and the Hudi Spark bundle. They ship in the XTable Spark runtime jar from 0.5.0, so no other XTable jar is needed.

Put these jars on the classpath of the driver and the executors. Use spark.driver.extraClassPath and spark.executor.extraClassPath rather than --jars, so that XTable and Hudi are loaded by the same class loader. The versions below are for Spark 3.5; use the bundles that match your Spark version.

  • org.apache.xtable:xtable-spark-runtime_2.12:0.5.0-incubating
  • org.apache.hudi:hudi-spark3.5-bundle_2.12:1.2.1
  • org.apache.iceberg:iceberg-spark-runtime-3.5_2.12:1.9.2

spark.sql.extensions must list the Iceberg extensions first and the XTable extensions second, and Hudi needs the Kryo serializer:

spark.sql.extensions=org.apache.iceberg.spark.extensions.IcebergSparkSessionExtensions,org.apache.xtable.spark.extensions.XTableSparkSessionExtensions
spark.serializer=org.apache.spark.serializer.KryoSerializer

The extensions work with any Iceberg catalog that Spark is configured with.

Running queries​

The extensions find the index by themselves: when a query filters an Iceberg table, they look for the Hudi metadata in the data path of the table. When a filter compares an indexed column with literals, for example email = 'x' or email IN ('x', 'y'), possibly combined with other filters by AND, the extensions look the values up in the index and read only the files that hold them. The query returns the same rows as without the index.

SELECT * FROM prod.db.customer WHERE c_email_address IN ('a@example.com', 'b@example.com');

DataFrame reads use the index the same way:

from pyspark.sql.functions import col

spark.table("prod.db.customer").where(col("c_email_address") == "a@example.com")
spark.read.format("iceberg").load("prod.db.customer").where(col("c_email_address") == "a@example.com")

At the INFO level of the org.apache.xtable logger, the driver log shows for each query whether the index was used and how many files it selected, for example Using the index of prod.db.customer on c_email_address for 1 keys: reading 1 of 64 candidate files.

When the index is not used​

The query reads the table as usual, so results stay correct, when:

  • the index was not synced with the current snapshot of the table. The driver log has a warning that names the snapshot of the index and of the table; run the sync job to use the index again.
  • a sync, a rollback or a rebuild changes the index while the query looks keys up in it.
  • the query reads an older snapshot (VERSION AS OF, TIMESTAMP AS OF, snapshot-id, as-of-timestamp), a branch, a tag, or the changes between snapshots (start-snapshot-id, end-snapshot-id).
  • the scan is small. A lookup runs a Spark job, which costs more than reading a few files. The index is used only when Iceberg's own partition and min/max pruning leave at least spark.xtable.index.pruning.minCandidateFiles files or spark.xtable.index.pruning.minCandidateBytes bytes to read.
  • the filter has more than spark.xtable.index.pruning.maxKeys values.

When a query fails​

A query with a filter on the indexed column fails when the column was renamed, or its name given to another field, after the index was synced. The index keys the column by name, so it would select the files of the old field. Remove the index and rebuild it after the next commit to the table, or turn the index off for the session.

Settings​

SettingDefaultMeaning
spark.xtable.index.pruning.enabledtrueUse indexes for queries
spark.xtable.index.pruning.minCandidateFiles32Minimum files a scan reads before an index is used
spark.xtable.index.pruning.minCandidateBytes1073741824Minimum bytes a scan reads before an index is used
spark.xtable.index.pruning.maxKeys10000Maximum values of a filter that is looked up

To read tables without their index, for example while an index is repaired, turn the index off for a session without removing the jar:

SET spark.xtable.index.pruning.enabled=false;

Limitations​

  • Only Spark sessions with the extensions use the index. Other engines read the table as usual.
  • Joins, subqueries, MERGE, UPDATE and DELETE do not use the index.
